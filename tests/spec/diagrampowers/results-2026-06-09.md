## Target B — drawio shape-index — VERDICT: redundant for the case tested

Deterministic scoring against confirmed ground truth
(`mxgraph.aws4.{lambda,s3,dynamodb,api_gateway}`):

| Trial | B-RED (no index) | B-GREEN (index delivered) |
| ----- | ---------------- | ------------------------- |
| t1    | **4/4**          | **4/4**                   |
| t2    | **4/4**          | n/a                       |
| t3    | **4/4**          | n/a                       |

**B-RED = 4/4 across all three trials** — the model reliably knows these tokens; not
a lucky single draw.

- **B-RED t1 = 4/4.** The bare model emitted all four exact `resIcon=mxgraph.aws4.*`
  strings _with the full `resourceIcon` style boilerplate_ (connection-point array,
  per-service brand `fillColor`, `aspect=fixed`), from memory, with **zero** tool
  calls and no index present.
- **B-GREEN t1 = 4/4.** Genuinely consulted the index (6 Bash queries) and reached
  the same four tokens. It added value the index does **not** provide: a
  `NEEDS HUMAN POLISH` flag, the render-to-SVG step, and house-style gap notes
  (font, monochrome-vs-brand-colour). That value is the drawio skill's _process_
  content, not the shape-index.

**Read:** for the four most common AWS service icons and a frontier model, the
10k-shape index is **redundant** — it did not change the icon outcome. This is a
genuine over-engineering signal for the index _in the case tested_.

**Honest limits (do not overclaim):**

1. The battery picked the **easiest, most-common** AWS icons — exactly where a
   capable model is most likely to have memorised the tokens. The index's real value
   proposition is **long-tail / obscure shapes** (Azure, GCP, K8s, Cisco, rare AWS)
   and **weaker models** (Sonnet/Haiku) that hallucinate. Neither was tested.
2. The finding condemns the **shape-index artifact for common icons**, not the whole
   `tech-diagramming-drawio` skill (which added real non-index value above).

**Next to settle the index's fate:** a second battery of ~8 long-tail/non-AWS icons
× {Opus, Sonnet, Haiku}. If RED stays ≥3/4 across vendors and tiers, retire the
index; if RED collapses on long-tail or on weaker models while GREEN holds, the index
is load-bearing and should stay (and the over-engineering is only in testing it on
easy cases).

## Target A — tool-selection routing — VERDICT: largely over-engineered for _choice_ at modest complexity

Two axes per scenario: **competence** (render-don't-draw, version-controlled,
sensibly stored) and **house-match** (matches the umbrella's prescribed tool).

| #  | Need                  | Umbrella | A-RED t1 choice                        | Competent? | House?          |
| -- | --------------------- | -------- | -------------------------------------- | ---------- | --------------- |
| A1 | login message flow    | PlantUML | Mermaid `sequenceDiagram`              | ✅         | ✗ (Mermaid)     |
| A2 | order state lifecycle | PlantUML | Mermaid `stateDiagram-v2`              | ✅         | ✗ (Mermaid)     |
| A3 | service architecture  | D2       | Structurizr DSL / PlantUML C4          | ✅         | ✗ (Structurizr) |
| A4 | DB schema + FKs       | D2       | Mermaid `erDiagram` / DBML             | ✅         | ✗ (Mermaid)     |
| A5 | README pipeline       | ASCII    | Mermaid `flowchart` in README fence    | ✅         | ✗ (Mermaid)     |
| A6 | icon-rich AWS deck    | draw.io  | **draw.io + AWS icons + exported SVG** | ✅         | ✅              |

- **A-RED: competence 6/6, house-match 1/6 — identical across all three trials.**
  The bare model picked competent, version-controlled, render-don't-draw tools for
  every item, stored them sensibly (`docs/diagrams/*.mmd`, CI-rendered SVG), and
  **nailed the subtlest call** — A6 to draw.io with the AWS icon set + exported image,
  no hand-pixel trap. The picks barely vary run-to-run (Mermaid for A1/A2/A4/A5,
  Structurizr-or-C4 for A3, draw.io for A6). Notably it **never reaches for D2** — the
  house tool for A3/A4 — so D2 is the choice the skill most changes.
- **A-GREEN t1: competence 6/6, house-match 6/6** — PlantUML, PlantUML, D2, D2,
  ASCII, draw.io, each with the `source + rendered .svg alongside` storage
  convention. The skill content was clearly in play (the J-table routing and the
  source+SVG pair are its signatures).

**Read:** the umbrella's routing does **not rescue a capable model from bad tool
choices** — RED was already competent and even got the hardest call right. The entire
RED→GREEN delta is **house preference** (Mermaid/Structurizr → PlantUML/D2/ASCII)
plus the storage convention. Whether the house toolchain _beats_ what RED chose is
**asserted by the skill, not demonstrated by this test** — Mermaid renders natively
on GitHub and is arguably better for A5 (README). So the elaborate J1–J8 table +
tool-strength matrix + decision tree is, **for tool choice at modest complexity,
largely over-engineered**: its real job is enforcing a house toolchain + conventions,
not preventing mistakes.

**Honest limit:** the scenarios are **modest**. The umbrella's genuinely non-obvious
guidance — _decompose-before-escalate_, complexity escalation, "measure edge
crossings, not box count," behavioural-vs-structural layout failure modes — was
**not exercised**, because none of the six needs pushed a tool past its autolayout
limit. That is exactly where routing might earn its keep.

**Next to settle the routing's fate:** a high-complexity battery (e.g. a 40-node
service graph with dense crossings; a 12-message sequence; "make this AWS diagram not
a tall strip") where naive tool choice visibly degrades. If RED degrades and GREEN's
decompose/escalate guidance saves it, the apparatus earns its size; if RED copes,
trim the umbrella to a short house-preference + storage-convention rule.

**Read:** for **Opus and Sonnet** — the tiers that actually run these skills — the
shape-index is **redundant even on obscure cross-vendor icons**. The only tier that
misses is Haiku, and (a) it is out of scope for this project's audience, and (b)
GREEN·Haiku shows the index does not even rescue it in practice (the weak model never
activates/queries it). Net: the 420 KB shape-index earns **nothing** for the models
that matter. The earlier "long-tail untested" hedge is resolved — the index is **not
load-bearing for Opus/Sonnet**; treat it as removable.

## Bottom line

We have **evidence**, not vibes, scoped to the tiers that matter (**Opus/Sonnet**;
Haiku is not this project's audience):

- **Shape-index → cut-eligible.** Redundant for Opus/Sonnet on both common _and_
  long-tail icons (8/8 each). Its only theoretical audience (weak models) doesn't use
  it. The drawio skill's _process_ content (polish flag, render-to-SVG) is separate
  and survives.
- **Routing apparatus → over-engineered for tool _choice_.** Opus picks competently
  unaided (6/6, 3× stable); the delta is house-preference + storage convention, not
  mistake-prevention. **Still open:** high-complexity layout escalation
  (decompose-first, edge-crossing) — the one genuinely non-obvious part — is untested.

Per the archpowers precedent ([[archpowers-bundle-design]]): capable models apply
best-practice unprompted, so "encode a competent default as elaborate content" needs
a RED test. These two RED phases passed on their own for the easy cases — the burden
is now on the hard-case batteries to show the content is load-bearing.
